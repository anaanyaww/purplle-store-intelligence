# DESIGN.md — Store Intelligence System

## Architecture Overview

The system is an end-to-end pipeline: raw CCTV footage → structured events → real-time analytics API.

**Five stages:**

1. **Detection Layer** (`pipeline/detect.py`): YOLOv8n detects persons in each frame. ByteTrack (built into ultralytics) maintains persistent track IDs across frames. Runs on Mac CPU or Apple Silicon MPS.

2. **Zone Mapper** (`pipeline/zone_mapper.py`): Maps bounding box centroid coordinates to store zones using confirmed camera placements. Single-zone cameras (ENTRY, SKINCARE, BILLING) return their zone directly. CAM_MAKEUP splits the frame: left 35% = FOH_CENTRAL, right 65% = MAKEUP_FLOOR
(calibrated via Claude Vision — see CHOICES.md Decision 1).

3. **Staff Detector** (`pipeline/staff_detector.py`): Three-tier detection: (1) Structural rule: the stockroom area visible in the footage had zero customers — only staff accessing inventory — validating a 
100% staff classification without needing a classifier. (2) HSV colour analysis — staff wear all-black uniforms confirmed from footage, threshold V<60 on >55% of torso pixels; (3) Behavioural — tracks with >90 min cumulative dwell crossing ≥3 zones are flagged.

4. **Event Emitter** (`pipeline/emit.py`): Stateful per-track registry. Emits ENTRY, EXIT, ZONE_ENTER, ZONE_EXIT, ZONE_DWELL (every 30s), BILLING_QUEUE_JOIN, BILLING_QUEUE_ABANDON, REENTRY. Re-ID via HSV colour histogram cosine similarity — departed track returning after 60–3600s with similarity ≥0.82 triggers REENTRY instead of ENTRY. REENTRY requires a confirmed prior EXIT event; track loss/recovery (occlusion behind shelves) emits ZONE_ENTER to continue the session rather than inflating REENTRY counts. This corrected an early pipeline bug where 39 false REENTRYs were generated by the Re-ID threshold matching new customers to departed tracks.

zone_hotspot_x and zone_hotspot_y fields are included in ZONE_ENTER 
event metadata per Purplle's sample_events.jsonl reference format. 
Current values are null — bounding box centroids are computed during 
detection but were not plumbed through to the event schema in this 
version. The field is present for schema compatibility.

5. **Intelligence API** (`app/`): FastAPI + SQLite. Ingests event batches, maintains session table (entry→exit per visitor_id), correlates POS transactions with billing zone presence (5-minute window), computes real-time metrics.

## Data

- **Store:** Brigade Road, Bangalore — `STORE_BLR_002` (internal: ST1008)
- **Footage:** 5 cameras, April 10 2026. CAM_BILLING is ~2 min (20:11–20:13 IST); others ~15–20 min
- **POS:** 24 unique orders, 12:15–21:40 IST, loaded into SQLite at API startup
- **Timestamps:** Extracted via EasyOCR from CCTV overlay (DD/MM/YYYY HH:MM:SS), validated with 3-frame consistency check, fallback to hardcoded values confirmed from footage screenshots

`unique_visitors` is defined as distinct visitor_ids from floor cameras (CAM_SKINCARE, CAM_MAKEUP, CAM_BILLING) during their 20:10–20:15 IST coverage window — the internally consistent population for all metrics. CAM_ENTRY's 12:00–12:04 window covers a separate visitor cohort and is reported separately as `entry_camera_events: 23`.

CAM_ENTRY's glass facade exposure to Brigade Road foot traffic is a deployment reality for high-street beauty retail. Approximately 45 people were visible through the facade during the entry camera window; direction-of-travel filtering (inbound = movement perpendicular to threshold, toward camera) excluded most passersby, but software-only entry detection on glass-fronted stores has a structural false positive floor. The production fix is a physical IR beam counter at the threshold. We report floor-camera visitors (49) as the primary metric, with entry_camera_events (23) as a supplementary signal for the separate noon-hour observation window.

Staff events outnumber customer events 5:1 (924 vs 188), reflecting continuous staff movement through all zones. Some customers in dark clothing may be flagged as staff by the HSV classifier — making `unique_visitors` a lower bound as well as subject to the upper bound constraints from passerby detection.

## AI-Assisted Decisions

**1. Staff detection strategy**
Claude initially suggested uniform colour histogram alone. After seeing the footage, I observed all staff wear all-black — this was confirmed and made the colour classifier viable as a primary signal. I added the backroom structural rule (anyone in stockroom = staff, no classifier needed) and the behavioural fallback as safety nets. The AI suggestion was good but I shaped it with footage observation.

**2. Zone merging for FOH/FRAGRANCE/NAIL_UNIT**
I asked Claude to map zones from the store_layout image. It suggested merging FOH, Fragrance, and Nail Unit into a single `FOH_CENTRAL` zone because CAM_MAKEUP covers all three from a single plane and sub-zone differentiation would be noisy. I agreed — better to be honest about resolution limits than emit unreliable zone events.

**3. CAM_BILLING data limitation**
Claude flagged that the billing clip is ~2:19 (vs 15–20 min for other cameras), making POS correlation methodologically thin. I incorporated this: the funnel endpoint includes a `note` field documenting the limitation, and the metrics endpoint returns a `data_confidence` warning when data is thin. I disagreed with one suggestion (to widen the POS correlation window to compensate) — that would inflate conversion rate artificially, which is exactly the "re-entry inflation" problem the spec calls out.
